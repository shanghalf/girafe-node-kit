GIRAFE node kit

Technical documentation: how the kit is built, how it runs a graph, how plugin nodes are isolated, and how API keys are handled.

Last updated 2026-11-11 (the kit's regular check is now a hello: POST /api/kit/hello tells GIRAFE which computer it runs on and what state its chain is in, so Settings › Node kit can show every computer you work on; before that, your own GIRAFE may read /api/info and /api/compat across origins, so its "Open the kit" button can say whether the kit is running, which version and which folder, and POST /api/open-folder opens a folder in your file manager; Align with GIRAFE: POST /api/align settles kit, GIRAFE, simulated and node versions in one call, local checks now follow the live GIRAFE instead of version.js, what only GIRAFE can decide is a warning not an error, and sending raises a node's version by itself; before that, tasks fields: POST /api/service-tasks reads a service's task history with the node's key, or its exported file; before that, a pasted key loses a leading "Bearer ", and a plugin node's panel got an "As in GIRAFE" tab with GIRAFE's own panel and 3D viewer, and the page may run WebAssembly for that viewer). Source of truth: this file, docs.html, at the root of the repository. The plugin contract has its own file, HOST_API.md.

1. Overview

The kit is a small, local copy of GIRAFE's Promptmixer canvas, used to build plugin nodes: nodes written by anyone, run in a sandbox, that talk to GIRAFE only through a fixed contract (the host API). It runs entirely on the user's computer: a Node.js server on 127.0.0.1 and a web page served by it.

PrincipleWhat it means in the code
Zero dependenciesNode built-in modules only (http, fs, crypto, child_process, diagnostics_channel). No npm install. The page is plain JavaScript modules, no build step.
Your work survives the kitEverything of yours is in one workspace folder in your home, ~/GIRAFE kit workspace (kit/home.js), outside the kit's own files: every copy of the kit uses it, and an update or a new download never touches it. The kit's folder holds only the program (plus .runtime/ for a private Node). Delete both to remove the kit.
Same behaviour as GIRAFECore nodes, socket lettering, streams, Collect, the flow socket, node look and colours follow GIRAFE's own code.
Plugins are untrustedEach firing runs in its own process with Node's permission model and no environment; it sees only ctx.
Keys never leakEncrypted at rest, decrypted only for one call to their own service, every outgoing request checked and logged (section 5).

2. Install and start

For users

  1. Download the ZIP of the release branch, unzip it.
  2. Double-click Start GIRAFE kit (Windows).cmd or Start GIRAFE kit (Mac).command.

The starter (tools/start.ps1 on Windows, tools/start.sh on macOS/Linux):

  1. uses the computer's Node.js if it is version 22 or newer;
  2. otherwise downloads Node 22.22.0 from nodejs.org/dist into .runtime/ inside the kit, checks its SHA-256 against nodejs.org's SHASUMS256.txt (a mismatch deletes the file and stops), unpacks it;
  3. runs node kit.js, which starts the kit as a child process and watches it (see Update the kit); the kit opens the browser on http://localhost:4747 (the next free port if taken).

The Windows starter is a .cmd calling PowerShell with -ExecutionPolicy Bypass for that one script. Windows (SmartScreen) and macOS (Gatekeeper) warn on first open because the files are not code-signed.

For developers

node kit.js            # start and open the browser
node kit.js --no-open  # start only
PORT=5000 node kit.js  # another port
node kit.js --no-watch # run the kit in this process (no restart after an update)
npm test               # the kit's tests

Node 22+ is required: the plugin sandbox uses the --permission flag.

4. Architecture

Server and routes

kit/server.js, Node's http module. It listens on 127.0.0.1 only. Every request must carry Host: localhost or 127.0.0.1 (stops DNS-rebinding pages), and a write coming from another site's page (Origin header not this kit) is refused.

Run engine

kit/engine.js. A run takes the graph, orders the nodes (a loop is refused), and runs them level by level. The rules are GIRAFE's:

  • Values travel as text or file references { imageUrl, key, mime, name }.
  • Input sockets are lettered A, B, C… by the order the wires were drawn. Output sockets of a one-output node are one per wire and all carry the same output. Named outputs (Yes / No) each carry their own.
  • A node fed by a stream (For each, or anything after one, or a plugin that emits several packets) fires once per item. Other inputs keep their single value for every firing.
  • Collect waits for everything and sends one JSON list.
  • A node whose wired inputs all stayed empty is skipped, and so is what follows.
  • The square flow socket: when wired, the node runs only if something reaches it.
  • An error stops that node and its branch only.

The run state (status, per-node status/note/outputs/firings/logs, per-wire count/state, waiting questions) is held in memory and polled by the page every 350 ms. Runs are forgotten 30 minutes after they end. GIRAFE streams item by item instead of level by level; results are the same, only the order the lights change differs.

Plugin nodes and sandbox

A plugin is workspace/nodes/<id>/manifest.json + node.js (full contract: HOST_API.md). kit/plugins.js checks the manifest (id = folder, version, hostApi equal to the kit's, the girafe minimum version, outputs, fields, capabilities) and greys out a node that doesn't pass.

Every firing starts a new child process:

node --max-old-space-size=128 --permission \
     --allow-fs-read=<the node's folder> --allow-fs-read=kit/sandbox-child.js \
     kit/sandbox-child.js        (env: empty)
  • It can read its own folder only, cannot write to disk, cannot start processes or worker threads.
  • It has no environment variables: no keys, no paths.
  • It is killed after 60 seconds (host API 2: the limits.seconds of its manifest, up to an hour), and dies alone if it exceeds 128 MB.
  • It talks to the kit only through ctx, whose calls are IPC messages handled by the host side in plugins.js (emit, progress, log, file read/write, each checked against the manifest's capabilities).
  • No network but ctx.http. Before the plugin's code loads, sandbox-child.js (1) makes the network itself unusable: the functions every connection goes through (net.Socket.prototype.connect, Server.listen, UDP sockets, every dns function) throw, and syncBuiltinESMExports() makes import() see the same locked functions; (2) removes fetch, WebSocket, EventSource; (3) locks the module loader so http, https, http2, net, tls, dgram, dns, child_process, cluster, worker_threads, inspector, undici, module, vm, v8, repl, wasi can't be loaded by require, by process.getBuiltinModule, or (Node 22.15+, module.registerHooks) by import(). Until 0.10.1 only require was covered, and await import('node:net') gave a node the network (and the kit's own local API). The process also runs with --disallow-code-generation-from-strings (no eval, no new Function). Node's permission flags refuse native bindings, add-ons, processes, threads and disk writes. This is a lock inside the process, not an operating-system firewall; GIRAFE's server adds an empty network namespace when the machine allows it.
  • Bounded results. One value sent on is 5 MB at most, 40 MB per firing, a written file 25 MB. --max-old-space-size does not count Buffers, so on Linux the host also reads the process's real memory (/proc/<pid>/status) twice a second and stops a node past 768 MB (PLUGIN_RSS_MB). Host calls are looked up as own properties of the host table only.

Host API 1: key slots and ctx.http

A plugin that calls a service declares it in its manifest:

"capabilities": {
  "keys": [{ "slot": "gemini", "service": "gemini", "label": "Gemini API key" }],
  "network": ["generativelanguage.googleapis.com"]
}

The panel shows one key picker per slot (the user's keys of that service). The node calls ctx.http({ slot: "gemini", method, url, json }); the host side in plugins.js:

  1. checks the address is https and its host is in network;
  2. refuses login headers set by the node (authorization, x-api-key, x-goog-api-key, cookie…);
  3. with a slot: takes the key the user chose for it (node.keySlots), checks its service, adds the service's login header itself;
  4. sends through netguard.send() (same checks and log as the core nodes, with purpose plugin <id> · slot <slot>);
  5. returns { status, ok, json, text } to the plugin. The key never crosses into the plugin's process.

Manifests are checked: a slot's service must be anthropic, openai or gemini and its API host must be listed in network. Nodes written for host API 0 still run (SUPPORTED_HOST_APIS), without ctx.http. The first real plugin using it is workspace/nodes/gemini-image (GIRAFE's Generate image rebuilt as a plugin).

Host API 2: panel files, nodes with no outputs, kept runs, streams

Besides long runs, ctx.state, ctx.files.fromUrl and forms, host API 2 has three things a manifest declares (all checked by checkManifest, refused below host API 2):

  • "type": "file" fields (accept, multiple): the panel uploads through POST /api/files (pictures, or 3D models told by the file name) and stores the references in node.settings[key]. The plugin reads them with ctx.files.read, like a file that came on an input.
  • "outputs": []: no output socket is drawn; ctx.emit is refused; what run returns (a value or a list) is returned by runPlugin as shown and becomes the node's displayed output, going nowhere.
  • "display": "runs": after each firing round the engine hands what the node sent or showed to kit/node-runs.js, which keeps the last 10 runs per canvas node (newest first; 60 values, 40 000 characters each; file references only). The panel shows them as Latest and Earlier runs, pictures and 3D model cards included, with Forget these runs. GIRAFE's Result stack is this display.
  • "streams": true: one firing may send several packets with ctx.emit. The kit's engine counts what arrives and doesn't need it, but GIRAFE plans a run before it starts (which inputs are streams) and gives a node fed by an undeclared stream only the last packet. checkManifest accepts it (boolean, host API 2, not on a node with no outputs); listPlugins carries it.

The page

Two panels for a plugin node. As in GIRAFE (web/girafe-panel.js, styles web/girafe-panel.css) is the panel the node will have in GIRAFE's Promptmixer: same fields in the same order and words (title, Run from here, description and version, key picker listing every saved key, the manifest's fields, "It may", On the phone, status and output, Delete), and for "display": "runs" the Latest / Earlier runs list with GIRAFE's 3D viewer (web/vendor/model-viewer-4.4.0.min.js, Apache 2.0, the file GIRAFE serves; looks Natural / Matte / Clay / Studio / Bright, moves as chips). It follows GIRAFE's PromptMixerView.jsx (renderPluginFields), PhoneModel.jsx and viewerLook.js: when GIRAFE's panel changes, change these two files. Kit tools is the kit's own panel (manifest, problems, packaging, sending). The tab is remembered in localStorage (kit.panelTab). Core nodes have one panel. The 3D viewer unpacks compressed models with WebAssembly, so the page's policy allows 'wasm-unsafe-eval' and blob workers; still no outside script and no eval of text.

web/app.js builds the canvas with plain DOM and SVG: nodes (220 px cards, GIRAFE's classes and colours), wires (curves coloured by source, green when delivered, grey dashes when dead), pointer-event dragging, wheel zoom, the panel (fields from the kind or the plugin manifest), the Yes / No dock, the Keys dialog. Graphs autosave half a second after a change; Ctrl+Z undoes structural changes.

5. How keys are managed

The Prompt and Generate image nodes call outside services with the user's own API keys. The rule the code enforces:

A key exists in plain text only twice: when it is pasted (from the page to the kit, on the same computer), and in the kit's memory for the duration of one call to its own service. It is never written in plain text, never listed, never logged, never given to a plugin, and never sent anywhere but its own service's address, in its login header.

A key pasted with Bearer in front (copied from a code sample) is saved without that word: the kit adds it itself for the services that want it (OpenAI, Tripo). Tripo has two official addresses, openapi.tripo3d.ai and openapi.tripo3d.com; a Tripo key may go to either.

A key's life

  1. Paste. The Keys dialog sends { label, service, value } in one POST /api/keys to localhost. The page clears the field right after sending; nothing is kept in the page, nor in the browser's storage.
  2. Encrypt and save. keys.add() encrypts the value with AES-256-GCM (random 12-byte IV, authentication tag) and writes workspace/.kit/keys.json with file mode 600. At the same moment it saves a masked form (AIza…5678) and a fingerprint (first 12 hex of SHA-256), so the key never has to be decrypted to be shown. The service is guessed from the key's shape (sk-ant-, AIza, sk-) and can be changed.
  3. Listed masked. GET /api/keys returns id, label, service, masked form, fingerprint. keys.list() contains no call to decrypt.
  4. Decrypted for one call. Only keys.use(id, service) decrypts, and only the Prompt and Generate image nodes (and the model list) call it, right before their request. It also refuses a key of the wrong service (a Claude key in Generate image).
  5. Checked by the guard (below), then sent.
  6. Logged: time, purpose, key label, address, result. Never the key.

Plugin nodes use the same path through a key slot: the user picks the key in the node's panel, and the host adds it to the plugin's ctx.http request. The plugin's process never receives the key (section 4, Host API 1).

The paste step reports back: the server marks the network log before saving and counts after, and the dialog shows "Key saved, nothing left this computer" with the count (0) and the fingerprint. If anything had gone out meanwhile, the box turns red and points to the log.

Storage and encryption

FileHolds
workspace/.kit/keys.json{ keys: [{ id, label, service, enc, masked, fingerprint, createdAt }] }; enc = iv.tag.ciphertext in base64. Mode 600.
workspace/.kit/secret.key32 random bytes (base64), created on first use. Mode 600.

Both are in .gitignore. Deleting a key removes its entry. To start over, delete workspace/.kit/.

The secret sits next to the keys, on the same computer: the encryption protects against keys.json leaking on its own (copied, attached, pushed by mistake). It does not protect against someone who can read the whole folder as you. That is the same trust you give any app that remembers a password on your computer.

The network guard

kit/netguard.js. Every request the kit sends to the internet goes through netguard.send(url, init, { service, key, keyLabel, purpose }); the kit code has no other fetch. When a request carries a key, it is sent only if all of these hold, otherwise it is refused before leaving and logged as blocked:

CheckRule
AddressThe host is the key's own service: api.anthropic.com, api.openai.com or generativelanguage.googleapis.com; the GIRAFE link token only girafe.live, the market link token only market.girafe.live (OFFICIAL in the code).
Encrypted connectionhttps for the official hosts.
Key in the login header onlyx-api-key (Anthropic), authorization (OpenAI), x-goog-api-key (Gemini). A key found in the address, in the body or in any other header is blocked.

Test runs point the services at a fake local server with KIT_ANTHROPIC_URL, KIT_OPENAI_URL, KIT_GEMINI_URL; that address is then allowed for that service, and shown as allowed in the Network panel.

The watch and the log

The guard only covers requests made through it. To catch anything else, the kit subscribes to Node's diagnostics_channel events for every outgoing request of its process: undici:request:create (all fetch calls) and http.client.request.start (the http/https modules). A request that wasn't approved by the guard just before is logged as unexpected.

🔑 Keys › Network shows: requests sent, how many carried a key, blocked, unexpected, the allowed addresses, and the last 100 entries. Healthy: blocked 0, unexpected 0.

The page lock (CSP)

Every page response carries:

Content-Security-Policy: default-src 'self'; connect-src 'self'; img-src 'self' blob: data:;
  media-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self' 'wasm-unsafe-eval';
  worker-src 'self' blob:; object-src 'none';
  frame-ancestors 'none'; base-uri 'none'; form-action 'self'
Referrer-Policy: no-referrer

The browser enforces it: the page can only load scripts from the kit and only send requests to the kit. Even if the page's code were changed to send the pasted key elsewhere, the browser would refuse. The kit uses no CDN, no outside font or script.

What it doesn't protect

  • The browser itself. An extension allowed on all sites can read what you type in any page, this one included. Paste keys in a browser profile without such extensions if in doubt.
  • Other programs on the computer, and anyone with access to your account.
  • The service itself: the key has to reach its own service to work. Use keys with spending limits where the service offers them.
  • Plugin network lock is inside the plugin's process (module loader and globals), not an operating-system firewall. Plugins never hold keys, so they have none to leak either way.

How it's tested

test/ai.test.js, against fake Anthropic / OpenAI / Gemini servers (no real key, no cost):

  • keys.json contains no key in plain; the list shows masked forms only;
  • listing still works with a wrong secret (proof it never decrypts);
  • pasting a key makes no internet request;
  • a key aimed at another address, put in the address, in the body or in a wrong header is blocked, and the fake server receives nothing;
  • a fetch that bypasses the guard is caught as unexpected;
  • the log never contains a key;
  • each service receives its key in its own login header only;
  • the gemini-image plugin gets its key added by the host, and its process has no fetch, no network module, and no way to set a login header or reach an undeclared host.

6. Packages and the GIRAFE link

The kit works fully without a GIRAFE account. Linking one is optional and one click away; it lets you send your nodes to your account, where they run on GIRAFE's server, on all your devices, seen by you only. GIRAFE's side of this (the /link page, installs, versions, the marketplace) is being built next; the kit side and its protocol are described here.

Pack: the .gnode file

kit/package.js. 📦 Pack in a plugin's panel writes workspace/packages/<id>-<version>.gnode, one JSON file:

{ "format": "girafe-node-package", "formatVersion": 1,
  "id", "version", "hostApi", "girafe", "manifest",
  "files": { "<path>": { "sha256", "size", "data" (base64) } },
  "hash":   sha256 of the sorted lines "<path> <sha256>\n",
  "author": { "publicKey" (Ed25519, base64 DER) },
  "signature": Ed25519 over "hash",
  "packedAt", "kit" }
  • All plain files of the node's folder, except dotfiles, node_modules/ and other packages; links are refused; 64 files and 10 MB at most.
  • The author key pair is made on the first pack: workspace/.kit/author-ed25519.pem (mode 600). Only the public key ever goes in a package.
  • verify(pkg) is what GIRAFE runs on upload: every file against its checksum, the hash against the file list, the signature against the author key, file names (no .., no absolute paths), the manifest (same checks as the kit), id and version agreeing with the manifest. GIRAFE remembers the author key of each node in an account: a later version signed by another key is refused.

Packs: the .gpack file

Tasks fields (kit/service-tasks.js, web/tasks-field.js; rules in HOST_API.md, Tasks fields). A tasks field names a key slot; the panel calls POST /api/service-tasks { plugin, field, keyId, before?, csv? }. The route finds the field, its slot's service and that service's billing entry (pack first, then the node's). With csv it parses the exported history file by billing.csv; otherwise it reads billing.history with the chosen key (decrypted in memory, sent through netguard.send() to the service's own hosts only), one window of maxDays ending at before (default now; a 400 on the first page retries once ending 31 minutes ago), following next/cursorParam or {page}, 30 pages at most. It answers { tasks: [{ taskId, type, model, status, units, createdAt }], from, to }: successful tasks only, each id once, newest first, 1000 at most. Nothing is stored server side: the panel keeps the loaded list and the chosen ids in the node's settings. Tested in test/service-tasks.test.js (fake history with a cursor, the real export format).

kit/packs.js. A pack is a folder in workspace/nodes/ with only a pack.json (rules in HOST_API.md, Packs): an id, a title, a version, its nodes and the key slots they share. listPlugins skips pack folders and gives each member a pack field; the palette shows members under the pack's title (right-click the title for GitHub). The pack's key choice is stored by id only in workspace/.kit/pack-keys.json ({ packId: { slot: keyId } }); the engine runs a member with packs.keySlotsFor(id), the pack's keys, never the node's own. Routes: GET /api/packs, POST /api/packs/:id/keys { slot, keyId }, POST /api/pack { pack }, POST /api/girafe/send-pack { id }.

{ "format": "girafe-pack-package", "formatVersion": 1, "id", "version", "pack" (pack.json),
  "packFile": { "sha256", "size", "data" },
  "nodes": [ a full .gnode package for each node, in pack.json order ],
  "hash":   sha256 of the sorted lines "pack.json <sha256>\n" and "node:<id> <node hash>\n",
  "author": { "publicKey" }, "signature": Ed25519 over "hash" (the same key signs every node),
  "packedAt", "kit" }

verifyPack checks every node package as above, that they are all by the pack's author and match pack.json, the pack rules, the hash and the signature. Sending a member alone is refused (code: "in-pack"). Before a pack leaves, the kit checks GIRAFE says packs: 1 in its compat answer (GIRAFE 0.70.0) and that it can run every node; GIRAFE takes it at POST /api/kit/packs.

Connect to GIRAFE

kit/girafe-link.js: the OAuth 2.0 device authorization pattern (as GitHub's command line, or signing in on a TV).

  1. ☁️ Connect to GIRAFE → the kit calls POST /api/kit/link/start { kitName, kitVersion } on GIRAFE and gets { deviceCode, userCode, verifyUrl, interval, expiresIn }. A verifyUrl on another site than GIRAFE is refused.
  2. The dialog shows the short code (like GIRA-FE42) and a button opening verifyUrl. On GIRAFE the person logs in or creates an account, checks the code, and clicks Allow. The password is only ever typed on GIRAFE.
  3. The kit polls POST /api/kit/link/poll { deviceCode } every interval seconds until approved (with token and account { name, email }), denied or expired.
  4. The token is saved in the key bank as a key of service girafe: encrypted, never shown, and guarded like any key (it may only go to girafe.live, in the Authorization header). It can't be pasted by hand, and is not offered in key pickers. workspace/.kit/girafe.json keeps the account name and the key id.
  5. Disconnect (in the dialog, or Delete on that key) calls POST /api/kit/link/revoke and removes the token. GIRAFE will also list linked kits (Settings › Connected kits) with a Revoke button.

The token's power is decided by GIRAFE: sending and updating the account's own nodes, nothing else (no topics, graphs, keys). KIT_GIRAFE_URL points the kit at another GIRAFE (a local one, or a test server).

Send to my GIRAFE

☁️ Send to my GIRAFE (or Connect and send when not linked) packs the node and sends it: POST /api/kit/packages, body = the package, Authorization: Bearer <token>. GIRAFE answers { status: installed | updated, message }, refuses a version that isn't higher than the one in the account (409), and a 401 means the link was revoked: the kit drops it and asks to connect again. Each send is in the Network log as Send "<id>" <version> to my GIRAFE.

In GIRAFE (from GIRAFE 0.68.0, open to admin accounts first): the node appears in the Promptmixer palette under Your plugin nodes, on every device of that account and for nobody else. GIRAFE checks the package again (file hashes, signature), pins the author key per node id, keeps every version (Settings › Connected kits: pick a version to roll back, turn it off, remove it, cut a kit's link) and runs the node in the same kind of locked child process as the kit. Key slots are filled from GIRAFE's own Key bank; GIRAFE adds the key to the call itself, only toward that service's official host. A plugin node doesn't run in a graph shared with someone else.

Before sending, the kit asks GIRAFE what it runs (below) and refuses itself, with the reason, a node GIRAFE can't run: nothing is sent. GIRAFE checks again on arrival: 426 { code: "kit-outdated" } for a kit older than it accepts, 409 { code: "host-api" | "girafe-version" } for a node it can't run; both carry its compat answer.

Local test against a GIRAFE on your own machine: start the kit with KIT_GIRAFE_URL=http://localhost:3003. The link page may then be on another port of the same machine (the kit compares host names, not ports).

Publishing to the GIRAFE Market

kit/market-link.js, button 🛒 Market in the top bar and a GIRAFE Market box under Share this node (or under the pack box). Optional, like the GIRAFE link, and separate from it: the market has its own accounts.

  1. Link: the same device flow, against the market (KIT_MARKET_URL, default https://market.girafe.live): POST /api/kit/link/start, the person approves on /link?code=… (signed in on the market, never in the kit), the kit polls /api/kit/link/poll and gets an mk_… token. It is kept in the key bank as a key of service market (encrypted, never shown, can't be pasted, guarded by the network guard: only market.girafe.live, in the Authorization header). workspace/.kit/market.json keeps the account and the key id. Disconnect revokes it on the market (/api/kit/link/revoke); the market's My submissions page can cut it too (the kit then gets a 401, drops the key and asks to connect again).
  2. Submit: the signed .gnode / .gpack (the same file GIRAFE gets) to POST /api/kit/submit?notes=…. The market checks it (checksums, hash, signature), refuses a version not higher than the one on the market, and a package id already published under another author key.
  3. The market page: edited on the market (/submissions/:id, the page editor), which the kit opens after a submit; a new version starts with the page of the one before. Optional, for older setups: when the node's (or pack's) folder has a market/ folder, the kit then sends market/listing.json (tagline, description, tags, captions by file name, i18n.fr / i18n.vi) to /api/kit/submissions/:id/listing, cover.png|jpg|webp (the tile background) and the pictures (PNG, JPEG, WebP, GIF, 6 MB, up to 8) and videos (MP4, WebM, 80 MB, up to 2) one by one to /api/kit/submissions/:id/media (raw body; ?role=cover for the background). Files are sorted by name. market/ is never packed (package.js SKIP): GIRAFE only gets the node.
  4. Review: every version, the first and each update, waits for a market admin, who approves (a new item, or a new version of the item that already carries this package id) or refuses with a note. The kit's 🛒 Market window lists the account's submissions and where they stand.

Billing: what a service costs

kit/billing.js. A node manifest or a pack.json may carry "billing" (rules in HOST_API.md, Billing; same checks as GIRAFE's checkBilling): per key service, the unit, a default price per unit, and optional balance / history GET calls (https, on the service's own hosts from netguard.OFFICIAL, since GIRAFE sends the user's key there) and a csv column map. A node reports a run's spend with ctx.usage; plugins.js's usage host call finds the entry (the pack's first, then the node's - billingFor), checks the report (a declared service, units 0 to 1e6, at most 500 per firing), writes a 💲 line in the node's log and answers { recorded, usd }. The kit records nothing else and makes no balance or history calls; that is GIRAFE's part. compat.checkNode / beforeSendPack refuse to send billing to a GIRAFE whose /api/kit/compat doesn't say billing: 1 (0.73.0 and newer).

6a. Signing in and leaving a computer

kit/session.js. Until the kit is linked to a GIRAFE account (the device link of section 6), every /api/ route answers 401 { code: "signin" } except /api/info, /api/compat, /api/update and /api/session*; the page shows only the sign-in screen. GIRAFE_KIT_NO_SIGNIN=1 lifts the gate (scripts only).

  • Routes: GET /api/session (signed in, account, trust, pending code, note), POST /api/session/signin { trust: "mine" | "passing" } (starts the device link), POST /api/session/beat (the page, every 30 s), POST /api/session/check, GET /api/session/unsaved, POST /api/session/leave { erase, force }.
  • Trust is kept in .kit/session.json with the last beat. passing: when no beat came for KIT_IDLE_MS (5 minutes), checked every minute and on start, the kit leaves with erase.
  • Leave with erase: saves every node of yours GitHub doesn't hold as it is here (github.save, states new / changed / deleted); stops with 409 { code: "unsaved", unsaved } when a node can't be saved (no GitHub, conflict, newer on GitHub) unless force (asked by name on the page, never automatic); then disconnects the market and GIRAFE (revoke) and removes everything in the workspace except the shipped example nodes, and restarts.
  • Remote cut, and the hello: on start and every 3 minutes the kit calls POST /api/kit/hello on GIRAFE (Bearer) - the same question as the older GET /api/kit/me ("am I still signed in?"), with news. A 401 drops the link here (signed out, a note on the sign-in screen); a 404 means a GIRAFE from before the hello, and the kit falls back to /api/kit/me by itself. Offline: the kit keeps going.
  • What the hello says (session.chainReport()): the computer's name (os.hostname()) and the port it serves on, the kit's version and host API, whether it starts with the computer, the GitHub repository of nodes with how many nodes it holds and how many are not saved, whether the market is linked and under which name, and every pack and loose node here with its version and the hash a package of it would carry (package.hashNode / hashPack, the same hash without building the package). GIRAFE shows it in Settings › Node kit, so you can see the chain of each of your computers from any of them. Nothing private goes in it: no key, no path, no node contents - and the GitHub state is read from disk, never over the network, so a check stays instant.

6c. Your nodes on GitHub

kit/github.js, top bar GitHub. Keeps workspace/nodes/<id>/ in a repo of the user's (private is the default; a public repo has to be confirmed) as nodes/<id>/. It uses GitHub's REST API only: no git program, so every request goes through the network guard (service github, host api.github.com, token in the Authorization header).

Setup. The user makes an empty private repo and a fine-grained token limited to that repo with Contents: Read and write, and pastes the token in 🔑 Keys (recognised by its github_pat_ / ghp_ start). POST /api/github/connect { keyId, repo, allowPublic? } checks the repo through the token (404 = name wrong or token not for it; no push permission = refused; public = refused unless confirmed) and writes workspace/.kit/github.json: owner, repo, branch, key id (never the token), and per node the files as last saved or fetched (git blob ids).

States, by comparing this computer's files, that saved list, and the repo's tree: clean, changed (here; the palette button pulses), new (never saved, ＋), behind (GitHub newer, ⬇), conflict (both, pulses red), deleted (removed from GitHub, still here), remote (only on GitHub, listed under Your nodes to get it). Local state is read every 5 s without internet; GitHub is checked every 2 minutes and on demand.

Operations (right-click a node under Your nodes, or a plugin node on the canvas):

  • Save to GitHub (POST /api/github/save { id, message, mine? }): commit and push in one step. Files are scanned first; anything that looks like a key (Anthropic, OpenAI, Google, GitHub, Resend, Tripo, kit token, a private key block) stops the save before anything is sent. Refused when GitHub is newer or both changed, unless mine. An empty repo is started with a README. Blobs are uploaded only when GitHub doesn't have them; the commit's tree changes only nodes/<id>/; the branch is moved without force (someone else moved it = "try again", nothing lost).
  • Take GitHub's version / Undo my changes (POST /api/github/update { id }): every file is downloaded and its blob id checked before the folder is touched. Work that exists nowhere on GitHub is first copied to workspace/.kit/backups/<id>-<time>/.
  • See my changes (GET /api/github/diff?id=): per file, and a line diff for text.
  • History (GET /api/github/history?id=) and Put this one back (POST /api/github/restore { id, commit }): an older version goes in the folder as a change, to save as the latest; same backup rule.

Only node folders are read for upload; .kit/ (keys, signing key, settings, backups) and graphs/ are never read by this module. File names must match a strict pattern; files over 20 MB, more than 300 files, node_modules and .git are not uploaded. "Stop using GitHub" forgets the repo here; nothing is deleted anywhere. Fake GitHub for tests: KIT_GITHUB_URL.

6b. Saved answers (cache)

kit/cache.js, workspace/.kit/cache.json, the newest 500 entries. The key is a SHA-256 of what defines the request:

  • Prompt: service, model, final text, picture file keys;
  • Generate image: model, format, size, final text, reference picture keys (the picture file itself stays in .kit/files/).

Same request = the saved result, no call, no cost (the node says so). "Always ask again" / "Always make a new picture" skip it. Keys are not part of the cache key and never stored in it.

9. Versions and releases

Three numbers, in kit/version.js:

NumberMeaning
KIT_VERSIONThe kit itself.
GIRAFE_VERSIONThe GIRAFE release the kit simulates. A manifest's "girafe": ">=x.y.z" is checked against it.
HOST_APIThe plugin contract (2). A manifest's hostApi must be one of SUPPORTED_HOST_APIS (0, 1 and 2). A change an older GIRAFE can't run bumps it (host API 2 added long runs, state and downloads); the previous ones stay supported for a while.

Kit and GIRAFE: matching versions

Both sides know the other's version, and each says plainly what doesn't match.

  • GIRAFE → kit: GET <girafe>/api/kit/compat (no login, no key) answers { girafeVersion, hostApi, hostApis, minKit, keyServices, kit: { repo, branch } }. Every /api/kit/ answer also carries X-Girafe-Version and X-Girafe-Host-Apis. The kit keeps the last answer in workspace/.kit/compat.json (10 minutes, and as "last known" when offline).
  • Kit → GIRAFE: every call to GIRAFE carries X-Girafe-Kit-Version and X-Girafe-Kit-Host-Api. GIRAFE answers 426 kit-outdated to a kit below minKit (or that doesn't say: kits before 0.4.0) when it links or sends; revoking still works. Settings › Connected kits in GIRAFE shows each linked kit's version and marks an outdated one, and marks an installed node whose host API GIRAFE no longer runs (GIRAFE also refuses to run it, with the reason).
  • The newest kit: the release branch's package.json, checked once an hour. A git clone reads it with git fetch <remote> release + git show FETCH_HEAD:package.json (your own git login, so a private repository works; listed in the Network log as a git call; the working copy is not touched). Otherwise, or when git fails, from raw.githubusercontent.com, which answers 404 for a private repository.

Per node, before sending (compat.checkNode): its hostApi must be one GIRAFE runs, its "girafe": ">=x" must be met by GIRAFE's real version, and each key slot's service must be one GIRAFE offers.

Local checks follow the live GIRAFE, never the kit's own guess (since 0.13.0). kit/plugins.js rules() reads kit/compat.js known() — the last thing GIRAFE actually said about itself, no network call — and falls back to kit/version.js only for a kit that has never reached a GIRAFE. The numbers in version.js are a fallback, not a rule: a kit must never be stricter than the GIRAFE it is linked to.

And only what the kit itself cannot do is a blocking problem. checkManifestFull() returns { problems, warnings }: a hostApi outside the kit's own SUPPORTED_HOST_APIS is a problem (nothing here could run it), while an unmet "girafe" range, an unknown field type, capability or key service, and a hostApi newer than the linked GIRAFE are warnings — shown under "Worth knowing", the node still runs and can still be sent, and GIRAFE decides on arrival.

Cross-origin reads, for GIRAFE's "Open the kit" only. GET /api/info and GET /api/compat answer Access-Control-Allow-Origin when the request's Origin equals compat.girafeOrigin() — this kit's own GIRAFE (KIT_GIRAFE_URL, else girafe.live) — and nothing else, ever. Writes are unaffected: a non-GET from another origin is still refused with 403. Without this, GIRAFE's button had to fire a link into the dark and let the browser say "this site can't be reached".

Align with GIRAFE (one button)

POST /api/align → kit/compat.js align({ id, send }). It force-refreshes /api/kit/compat, re-checks every installed node against that fresh answer, compares this kit with minKit and with the release branch, and returns { picked, girafe, kit, latest, updateAvailable, kitOld, nodes, steps, sent } — steps being the plain-words report the dialog shows (levels ok | info | warn | block).

  • With send: true and no id, it picks the node whose files were touched last (listPlugins() → changedAt, the newest mtime in the node's own folder) and sends it.
  • kit/girafe-link.js send() handles GIRAFE's one self-fixable refusal: a 409 { code: 'version-not-higher', installed } (older GIRAFEs only say it in words) makes raiseVersion() rewrite just the version number in manifest.json — a regex on that one line, so the author's formatting and comments survive — and send once more, reporting raisedTo.
  • It never rewrites anything else to make a check pass. A node that really needs a newer GIRAFE waits for one, and the report says so.

Update the kit

🔄 Versions and updates (the version badge, the alert button, or the Versions box) shows both sides and offers ⬆ Update the kit (kit/updater.js):

  • A git clone (a .git folder): git pull --ff-only on its own branch, only when none of the kit's own files are changed (the dialog lists them otherwise) and the branch has an upstream. git runs as its own program; the kit logs it in the Network list.
  • A downloaded zip: the release branch's zip from codeload.github.com, through the network guard (no key, 40 MB at most). Checked before anything changes: one top folder, no .. or absolute names, CRC of every file (kit/zip.js, no dependency), package.json and kit/version.js agree on a version newer than this one, the Node version it needs is met. Unpacked to workspace/.kit/update/staged-…, the kit's current files copied to workspace/.kit/update/backup-<version>-… (the two newest kept), then swapped in. A failure while swapping puts the backup back at once.
  • Never touched: workspace/ (nodes, graphs, keys, files, settings), .runtime/ (the private Node), .git/, node_modules/.
  • Restart and roll back: kit.js is a small watcher that runs the kit as a child process. After an update the kit exits with code 75; the watcher starts it again on the same port and the page reloads by itself. The new kit marks the update as kept once it listens (workspace/.kit/update/last.json). If it stops before that, the watcher puts the backup back (or git reset --hard to the previous commit) and starts the previous version; the page then says the update was put back. The watcher itself is the copy that was running, so keep pending.json's shape compatible across versions.

Tested end to end (test/versions.test.js): a copy of the kit updated from a fake release while running, restarted on it with the workspace intact, then a release that crashes on start put back by itself; a git clone pulled and rolled back; a clone with changed kit files refused.

Branches: main is development, release is what users download. Shipping a version: bump KIT_VERSION and package.json, add the CHANGELOG.md entry, then move release to that commit and tag it vX.Y.Z.
